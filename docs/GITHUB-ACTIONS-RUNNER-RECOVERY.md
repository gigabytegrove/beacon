# GitHub Actions runner recovery — Beacon

## Confirmed behavior, October 11, 2026

The private `gigabytegrove/beacon` repository's Windows, Linux, Android and server workflows are failing **before a runner starts**. The API reports completed/failed jobs with `runner_name=""` and **zero executed steps**. Re-running jobs produced the same result. This means no compilation, unit tests or packaging took place in those runs.

Do not diagnose Go, Gradle or Docker from zero-step jobs: no process ran to produce such an error.

## Check the owning GitHub account's Actions eligibility

1. Open the account/organization that **owns the private repository**, then **Settings → Billing and licensing → Budgets and alerts** (labels may differ). Check included Actions minutes, whether an Actions budget has a **$0 stop-usage** setting, payment restrictions, or other usage controls.
2. Open the repository **Settings → Actions → General**. Confirm Actions is enabled, the workflows' referenced actions are permitted, and GitHub-hosted runners are allowed.
3. Open **Actions** and inspect one of the failed workflows. If GitHub displays a banner describing payments, spending limits or account restrictions, address that exact cause in account billing/settings. There is **no basis to conclude a specific billing problem solely from zero steps**.
4. If allowance and settings are correct but nothing runs, contact **GitHub Support** with the failing run URLs/IDs and the exact `runner_name=""` / `steps=0` behavior. A backend Actions entitlement or payment problem cannot be repaired by changing Beacon's application code.

Official documentation: https://docs.github.com/en/billing/concepts/product-billing/github-actions

## No-paid-runner alternative

Beacon can be built on a **local Windows development computer** with Go/MinGW and Android Studio, and on a **local Linux build computer** with Go/GCC/OpenGL headers using the repository's `scripts/build-*` commands. This does not consume GitHub-hosted Actions minutes. The resulting compiled desktop binaries run without the SDK or Python installed on ordinary users' machines.

**Optional:** Configure a self-hosted GitHub Actions runner on a trusted, isolated build workstation. Never register arbitrary/untrusted public repositories with a self-hosted runner, and do not expose the Dokploy production host as a general-purpose CI executor. Runner installation involves independently reviewing trust, secrets, and update privileges; it is not required for Beacon to operate.

## What constitutes a verified release

- Windows: a nonempty `Beacon-Windows-0.8.0.exe` generated by `go build`, tested on Windows, with checksum.
- Linux: a nonempty `Beacon-Linux-0.8.0.tar.gz` generated by the Go build and installer scripts, tested on a Linux desktop.
- Android: a versioned APK created by a real Gradle build, installed and tested on an Android device.
- Backend: Docker image built and FastAPI tests run with a passing result, followed by a persistent-volume-safe Dokploy deployment.

The separate Go Beacon Probe binary only validates server connectivity/API; it **does not** validate any graphical application.


## Executable alternative: trusted self-hosted Actions runners

The workflows now support self-hosted Linux and Windows workers with **no skipped build steps**. Follow [Self-hosted Build Runners](SELF-HOSTED-BUILD-RUNNERS.md) for the exact GitHub registration commands and required labels. Once both workers show Online, choose the self-hosted runner location during a manual run or set GitHub Actions repository variable `BEACON_USE_SELF_HOSTED_RUNNERS=true` for all push jobs. The ongoing billing/entitlement status of GitHub-hosted runners is a separate problem; changing the runner target does not falsely mark that issue fixed.
